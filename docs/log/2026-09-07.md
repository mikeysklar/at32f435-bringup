- CN6 plugged into bravo. AT-Link-EZ enumerates as `2e3c:f000 Artery Technology
  CMSIS-DAP`: sysfs path `3-5.2.1`, serial `1ACD5803008062301017B002`, bcdDevice
  `0200` (V2 firmware, so the DAP-v2 bulk interface is available), VCP at
  `/dev/ttyACM6`. First time any `2e3c` device has been on the bus.
- **No jumper change was needed.** Confirms UM_AT_START_F435 §3.8 as researched:
  there is no AT-Link isolation jumper (the AT-Link is separated only by snapping
  the score line), and it powers only from CN6. JP1/BOOT0 left at its default.
- **The udev rule is not needed on bravo.** `scripts/99-at32.rules` was never
  installed and probe-rs claims the CMSIS-DAP interface anyway. Left uninstalled;
  the attended sudo step in the resume note can be dropped unless a different host
  needs it.
- **`probe-rs info` cannot be used on this target.** It ignores `--chip` (warns
  "ignoring --chip option") and then fails auto-ID with "The connected chip could
  not automatically be determined". Without an explicit `--probe` it also tries to
  prompt for a probe index and dies with "Failed to parse probe index", because
  bravo has 11 probes attached. The working form is the one the scripts already
  use: `--chip AT32F435ZMT7 --probe 2e3c:f000:<serial>`.
- SWD attach verified read-only:
  `probe-rs read --chip AT32F435ZMT7 --probe 2e3c:f000:<serial> b32 0x08000000 4`
  -> `20012d68 08000221 0800094f 08000947`. Valid stack pointer into SRAM and a
  plausible reset vector, so the factory firmware is intact and the die answers.
- Target UID (0x1FFFF7E8, 3 words): `2030322f 21728000 0db4070c`.
- probe-rs 0.32.0 lists 20 AT32F435 variants, AT32F435ZMT7 among them.
- Factory flash backup (`at32-backup.sh`, 4032 KB) started; the UID file landed,

## M1 COMPLETE: flashed, running, verified

- `at32-flash.sh board_test.elf` -> probe-rs "Finished in 0.70s", then reset. One benign
  warning on reset: "Could not clear all hardware breakpoints: An ARM specific error
  occurred. Caused by: A timeout occurred during an operation."
- Flash readback at 0x08000000: `20060000 08000529 08000675 0800069d`, byte-identical to
  the ELF's `.isr_vector` (`00000620 29050008 75060008 9d060008` little-endian). The
  write landed.
- **The target executes.** AT-Link VCP `/dev/ttyACM6` at 115200 prints
  `Hello from TinyUSB\r\n` on repeat. That proves core, clocks and USART1 (PA9/PA10),
  and confirms JP4 is already in the "USART1" position, so the VCP is usable as a
  console from here on with no jumper change.
- Owner confirms a **blinking red LED** on the board. PD13 = LED2 is therefore the right
  pin. **Polarity is still unresolved**: `board_test` blinks at an even duty, so an
  inverted drive is visually identical. The ACTIVE_HIGH-vs-active-low question between
  the Zephyr fork's board dts and the TinyUSB BSP has to be settled by Zephyr blinky
  (M3), not by this.

## BUG in scripts/at32-backup.sh: the backup it wrote was not restorable

- `probe-rs read --chip ... b8 <addr> <len> --output FILE` (probe-rs 0.32.0) writes the
  **ASCII hex dump** to FILE, not a raw binary. The "flash-*.bin" it produced was
  `ASCII text`, 17,547,264 bytes = 516,096 lines x 34 (`"%08x: " + 8*"%02x " + \n`).
- The dump is lossless: converted to a real image, contiguous 0x08000000-0x083F0000,
  **4,128,768 bytes = 4032 KB exactly**, md5 `948e2bc961d51dd5c1c3c577c5f06357`, saved
  alongside as `flash-20260907-065757.image.bin` (+ `.image.md5`). Restore path is
  `probe-rs download --binary-format bin --base-address 0x08000000`.
- The script needs fixing before the next backup, or a future restore silently fails.
  The factory image itself is safe.
