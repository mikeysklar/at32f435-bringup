## LED polarity fix landed on a branch, and verified end to end

mikeysklar/zephyr-at32-module#1, branch `dts-led-active-low`, commit ac892a0. Three
lines: led2/led3/led4 `GPIO_ACTIVE_HIGH` -> `GPIO_ACTIVE_LOW`. The PA0 button is
deliberately untouched, its polarity has not been checked on hardware.

Verification, because the hardware test proves the wiring but not that Zephyr's
`gpio-leds` path then behaves correctly:

- Built Zephyr blinky against the module with the branch checked out. 16092 B flash.
  Generated devicetree shows `gpios = < &gpiod 0xd 0x1 >`, flag 0x1 = ACTIVE_LOW, so the
  change reaches the build.
- Stock blinky toggles at even duty and therefore cannot show polarity by eye. Built a
  scratch copy at `SLEEP_TIME_MS 6000` (test scaffolding in ~/at32/scratch-blinky, not a
  change to any repo) so console lines and SWD reads could be correlated without a race.
- PD13's output level is bit 13 of GPIOD `odt`. GPIOD base `0x40020c00` from the built
  devicetree; `odt` is the 6th 32-bit register in the HAL's `gpio_type`
  (cfgr, omode, odrvr, pull, idt, odt, ...), so **GPIOD_ODT = 0x40020c14**.
- Correlated a freshly arrived console line against an immediate `probe-rs read`:

      console OFF -> PD13 bit 1 (ODT 0x2000)
      console ON  -> PD13 bit 0 (ODT 0x0)      x3 each, 6/6 consistent

  Each read landed 0.2-0.36 s after the line, inside the 6 s window. First attempt at
  this was racy (matched buffered lines up to 6 s stale and gave a mixed result); fixed
  by draining the buffer and blocking for a fresh line.
- Conclusion: `led0` "ON" drives PD13 low, and low is lit. Zephyr's LED semantics now
  match the hardware.

CircuitPython reflashed afterwards and confirmed working, so the board is back in the
useful state. **The CDC tty number changes on every re-enumeration** (ttyACM20 ->
ttyACM13 across a reflash); find it from sysfs by walking `/sys/bus/usb/devices/*` for
idVendor 1209 and reading the interface's `tty/` entry, the same discipline as
`at32-find.sh` for the AT-Link.

### Debugging notes worth keeping

- A stock `cdc_msc` that enumerates nowhere looks identical to a hung board. Proved
  liveness instead of assuming it: `system_ticks` at 0x200024d8 (from `nm` on the
  ELF) climbed ~1150/s, and `blink_interval_ms` read 250 with `blink_enable` 1.
- First PD13 sampling run showed 8 identical reads and looked like a dead LED. It
  was aliasing between the ~0.65 s sample period and the 250 ms blink; sampling
  without a sleep showed both levels immediately.
- `probe-rs read` prints `<addr>: <value>`, so a regex for 8 hex digits matches the
  address first. Index the value, not the first match.
- The AT-Link VCP buffers output across sessions. A read that returns text from a
  previous firmware is stale queue, not the running image. Drain before reading.
